## 二、老P 六问答复与决策

### Q1 — 登录架构（你偏好"统一地址 + 按角色跳转"）
**采纳，并给落地建议**：
- 全平台**一个 `/login`**（手机号+密码），后端 `Login` 已返回 `role`，前端据此分发：
  - `teacher`/`head_teacher` → `/teacher`
  - `research_lead` → `/teacher`（科研池入口在侧栏）
  - `registrar` → `/teacher`（教务入口在侧栏）
  - `principal` → `/principal`
  - `it_admin` → `/it-admin`
  - `student` → 微信小程序（不在本仓库）
- 侧栏按角色显隐对应菜单（IT/教务/教研/校长入口仅对有权角色可见）。
- IT管理员若需临时用教师功能，后续加"切换教师视图"链接（v2.4 先不做的，记录待办）。

### Q2 — 模板是否需要示例数据行
**需要**。4 个 CSV 模板均含：① 字段说明注释行 ② 1–2 行示例数据。便于学校老师照填。

### Q3 — 教材版本：统一 or 分项
**默认全校统一（按年级×学科批量套用），支持逐项覆盖**：
- 预置库（`scope='platform'`）：语文=部编版/人教版/北师大版/苏教版；数学=人教版/北师大版/苏教版；英语=PEP/外研版/牛津版。
- 学校首次进入：按年级×学科复制平台默认 → 生成 `scope='school'` 行。
- 支持"批量设置"（整校/整年级）+ 单格"更换"（实验班可单独改某年级某学科甚至某班级）。

### Q4 — 角色模板初始化在 IT后台 还是 平台运营端？（你要求进一步说明）
**澄清概念**：
- "角色模板" = 角色集合 + 每种角色默认权限映射。当前权限映射是**硬编码在 `middleware.RequireRole` 里**的（哪些路由允许哪些角色），属于**平台级常量**，由各角色路由分组体现，不需要学校去改。
- 所以分两层：
  1. **角色定义（平台级）**：由代码/种子常量维护，**不在学校 IT后台 编辑**（也无需单独的"平台运营端 UI"——`platform_ops` 那组是给 SaaS 厂商管 token/license 的，跟角色无关）。
  2. **角色分配（学校级）**：学校 IT管理员把"预置角色"**套用到具体用户**——这就是"一键初始化"要做的：导入教师后，默认全部给 `teacher`，模板里标"是班主任"的给 `head_teacher`，等等。
- **结论**：**"一键初始化"在 IT管理后台操作**，套的是平台预置角色；平台级角色定义不在本仓库 UI 维护（代码常量 + 种子即可）。

### Q5 — 学生需要密码登录吗？
**不需要**。结论与现状一致：
- 学生端是**微信小程序**，凭 `WechatOpenID` 静默登录（无密码）。`User` 模型已有该字段。
- 初始化只创建**学生记录**（姓名/学号/班级/家长手机号），**模板不含学生密码列**。校内"学号"=学生在班里的编号（非教育学籍号），落 `User.student_number`，同校唯一、格式不强制。
- 学生与账号的绑定发生在小程序首次微信登录 + 家长认领（`ParentSignPage` 已有）时，不依赖学校预设密码。
- 教师则需要密码（他们走手机号+密码登录）：**教师初始密码 = 手机号后 6 位，首次登录强制修改**。

### Q6 — 批量导入的定义 + 部分成功/全回滚 + 增量变更
**定义（两阶段事务 + upsert，支持增量）**：
1. **预校验（dry-run，不写库）**：解析全部行 → 逐行校验（必填、手机号格式 `/^1[3-9]\d{9}$/`、手机号/学号唯一性、班级引用存在、班主任唯一、任课唯一）→ 返回每行的 成功/失败(原因)/警告 明细。**此阶段零入库**。
2. **执行（事务提交）**：用户点"确认导入"后，整批在**一个 DB 事务**内写入；中途任何错误 → **整批回滚**，库不变。
3. **增量 upsert（A3）**：同一学校**重复导入不报错**——按「手机号（教师/家长）/学号（学生）」匹配：已存在则更新（姓名/班级/学科等），不存在则新增。开学后插班生、信息更正，可直接重导或单条修正，无需整批撤销重导。
4. **事后回滚**：每批写入记录 `batch_id`；导入历史提供"撤销本批次" → 按 `batch_id` 事务删除该批所有记录（**全回滚**）。

**"可以部分成功，但允许全回滚"的落地**：
- 提供开关「跳过失败行并提交成功行」（**默认开启**，符合你说的"部分成功"）：预校验失败的行不写，成功行入库，并返回失败明细供修正后重导。
- 无论部分成功还是整批成功，都带 `batch_id`，随时可「撤销本批次」做**全回滚**。
- 关系型数据（学生→班级、任课→教师/班级）在预校验阶段已校验引用完整性，故部分成功不会产生"孤儿"数据。
- **转班/退学（A3 的 P1 部分）**：补 `POST /api/.../students/:id/transfer`（改 `StudentClass` 关联）与退学置 `left` 端点，不靠整批重导。

### 4 个导入模板（含示例行）
- `教师导入模板.csv`：姓名/手机号/任教年级/任教班级/任教学科/角色(teacher|head_teacher)/是否班主任（初始密码默认=手机号后6位，首次登录强制改密，模板不单列）
- `学生导入模板.csv`：姓名/学号/校区/年级/班级/家长手机号（**无密码列**；学号=校内编号，非教育学籍号）
- `班级导入模板.csv`：校区/年级/班级名称/班级类型(普通|实验)

### 导入顺序约束（依赖驱动，非强制锁死）
首次导入建议顺序：学校 → 班级(含校区) → 教师 → 学生 → 任课 → 班主任 → 家长（前端步骤条引导，预校验阶段引用完整性把关）。
因 A3 支持 upsert，**顺序不必强制锁死**：缺的依赖项在预校验会明确报错，修正后重导该行即可（无需整批撤销）。
