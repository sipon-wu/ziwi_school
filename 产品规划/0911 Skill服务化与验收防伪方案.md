# 0911 Skill 服务化与验收防伪方案

> 目标：把"由 Skill 生成 PPT / H5（含模板引用）"从**文档态**推进到**可执行、可验证、不可假绿**的服务态。
> 依据：《0910模板方案》（目标态）、《0910目标达成差异简报》（现状与根因）。
> 日期：2026-09-11 ｜ 原则：**先做最小可验证闭环，再展开；效果倒推验收。**

---

## 一、背景与要解决的问题

现状三个硬伤（详见《0910目标达成差异简报》）：
1. **工具层缺失**：`template.query / asset.search / slide.render / visual.check / story.render` 全库只在文档里；
2. **结构不差异**：PPT 所有模板共用全局 `EDU_LAYOUT_SKELETONS` 几何，`applyTemplate` 按内容 `inferEduLayout` 推断 → 换模板=换配色；
3. **假绿验收**：`verify_*.cjs` 断言"存在/字段传递"，`verify_style_diversity.cjs` 的 PPT 断言因 `PPT_IDS` 默认空而**静默不执行**。

本方案按"**确定性工具层 → 轻编排 → 验收防伪**"三层推进，并把"杜绝假绿"作为一等公民机制（第五章）。

## 二、总体架构

```
调用方（教师端 / 前端 / 小微）
        │  POST /api/ai/courseware/generate  (SSE 可选)
        ▼
┌──────────────────────────────────────────────┐
│  ai-service (FastAPI)                         │
│  ├─ /healthz                                  │
│  ├─ /api/ai/courseware/generate   （P1 受控编排）│
│  └─ /api/ai/courseware/tools/*    （P0 工具层） │
└───────────┬──────────────────────────────────┘
            ▼
┌──────────────────────────────────────────────┐
│  受控流水线（非全自主 ReAct）                  │
│  S0 澄清 → S1 解析 → S2 取风格/资产 → S3 生成 │
│  → S4 三关质检 → S5 交付入库                  │
│  · LLM 只出现在 S0/S2 匹配/S3 生成/S4 评审    │
│  · 工具调用由流程确定，不由 Agent 自由选择      │
└──────────────────────────────────────────────┘
            ▼
┌──────────────────────────────────────────────┐
│  确定性工具层（P0，纯函数 / HTTP 端点）        │
│  template.query · asset.search · slide.render │
│  visual.check · story.render                  │
└──────────────────────────────────────────────┘
```

**关键取舍**：不采用全自主 ReAct。理由：生成课件是**有固定 SOP**的任务，Agent 自由选工具只会带来非确定性（同输入不同结构）、更难测（假绿温床）、延迟与成本上升。System Prompt 保持轻量（只引导读 SKILL.md），但**SKILL.md 必须机器可执行**（工具带 schema、references 版本化、Skill 注册表）。

## 三、P0：确定性工具层（最高 ROI）

**为什么先做它**：它同时是"模板引用落地"的前提、两个服务化方案的公共底座、且**天然可测**（纯函数、无 LLM 发挥）。

### 3.1 工具接口草案

| 工具 | 入参 | 出参 | 确定性来源 |
|---|---|---|---|
| `template.query` | `{style_tag, stage, subject, scene?, kind:'ppt'\|'h5'}` | `{templateId, themeId, styleDNA:{colors,font,density,decorVocab}, skeletonClass}` | 词表映射，无 LLM |
| `asset.search` | `{styleId, stage, subject, need, scene?}` | `[{assetId, url, params}]`（数量 = need × 系数） | 匹配度排序，无 LLM |
| `slide.render` | `{outline, themeId, styleDNA, aspect}` | `{pptxModel}`（供 pptxgenjs） | 读快照渲染 |
| `story.render` | `{story}` | `{html}`（自包含 H5） | `buildStoryH5` |
| `visual.check` | `{html\|outline, themeId, styleDNA}` | `{issues[], metrics:{contrast, overflow, density, skeletonClass}}` | 规则 + 转图 |

### 3.2 强制契约（防"又变成换色"）

1. **渲染只读快照**：`slide.render` / `story.render` 只消费 `styleDNA` 与 `skeletonClass`，**不读 `template_id`**——避免"提示词改一次、历史课件外观全变"。
2. **模板必须产出结构差异**：`template.query` 返回的 `skeletonClass` 必须**真实驱动版式几何**，而不是仅换配色；同一内容喂不同风格，`skeletonClass` 或几何必须有可观测差异。
3. **资产只存形状**：`asset.search` 返回的资产只含形状/语义槽，颜色由 `styleDNA` 渲染时填入（对齐既有纪律）。

## 四、P1：轻编排（S0–S5 受控流水线 + SSE）

- 把 `api_server.py:509` 的单次 LLM 调用，改为**固定六步流水线**：S0 澄清 → S1 解析 → S2 取风格/资产（调 P0 工具）→ S3 生成 → S4 三关质检 → S5 交付。
- **LLM 只在判断点出现**：S0 澄清提问、S2 风格匹配兜底、S3 内容生成、S4 内容评审；工具调用与版式决策**由流程确定**。
- **SSE 流式**：`GET /query/stream` 或 `POST` + `text/event-stream`，逐步推送"已选风格 → 已取资产 → 生成中 → 质检结果"，提升可解释性（也便于验收时看到中间态）。
- **SKILL.md 机器可执行化**：为 `tools` 每项补 JSON schema；`references/` 纳入版本号；建 `Skill Registry`（id / version / status / tools / references）。
- **可观测**：每次生成留痕（skill 版本、工具调用参数与结果、质检分数），供归因与回归。

## 五、P2：验收防伪机制 ★（回答"为什么总是假绿"）

### 5.1 为什么"分析头头是道、做出来不是那么回事、还假绿"

| 根因 | 表现 | 证据 |
|---|---|---|
| **验收标准与产品目标脱节** | 验收定义在"接口通/字段有/页面能开"，产品要的是"肉眼可分" | 60h 验收止步于功能可用 |
| **断言"存在"而非"差异"** | 测 DOM 存在、字段传递 | `verify_courseware_style_p1.cjs:79-80`（只验 style_tag 回显） |
| **测规则存在而非视觉不同** | 测 CSS 里有 `.layout-china` 规则 | `verify_layout.mjs:46-48` |
| **默认跳过=静默通过** | 缺环境变量就 return，报告仍绿 | `verify_style_diversity.cjs` 的 PPT 断言依赖 `PPT_IDS`，默认空→不跑 |
| **只调内部函数，不跑真实链路** | 构造 markdown 直接调渲染器，绕过"生成→预览→发布" | 时序 bug 只在真实流程触发 |
| **无测试有效性自检** | 测试从没被"故意打破"验证过是否真能变红 | 假绿可长期存在 |
| **方案↔代码无对账** | 方案说"已做"，实际没做/做半 | "风格驱动骨架"部分落地 |
| **实现者自证验收** | 自己写测试自己过，无独立举证 | — |
| **主观目标无代理指标** | "好看/可分"被认为不可测→不测→目测→放水 | CSS 规则存在即"过" |

### 5.2 杜绝假绿的九条机制

**M1. DoD 前置 + 目标转译**
每个需求先写"验收断言"再动手；断言必须是**可观测差异**，禁止"存在性"当验收。
- 反例：~~页面含 `data-motif`~~
- 正例：同一内容用 theme A / theme B 渲染，`skeletonClass`、主色相角距（≥25°）、DOM 结构签名三者**至少两项不同**。

**M2. 差异式 / 对照式断言**
风格与模板类测试一律 **A/B 对照**（同输入 × 两种风格），断言"可量化不同"，而非"各自存在"。主观目标设**代理指标**：相角距、骨架类、结构签名差数、留白比例、卡片几何。

**M3. 测试有效性自检（反假绿核心）**
- **变异测试**：故意注入缺陷（如把 `themeId` 写死 `storybook`、把 `applyTemplate` 的 remap 去掉），若测试仍绿 → 该测试无效，必须修。
- **负控用例**：每个套件至少一条"已知必须红"的用例，CI 断言它确实红。
- **`skip = fail`**：因缺环境变量/数据而跳过的用例，必须显式标 **SKIP** 并在报告里计为"未验证"，**禁止 `return` 早退当通过**。

**M4. 真实链路 E2E（真数据回放）**
验收必须在真实浏览器跑完整流程（生成→预览→发布→扫码打开），并用**库内真实的 6 个 CwTheme id** 各回放一遍；不允许只构造数据调内部函数。

**M5. 方案 ↔ 代码 ↔ 测试 三方对账**
方案条目带 **ID**；提交信息与测试用例引用该 ID；脚本生成"方案覆盖矩阵"，**未覆盖条目在 CI 里红**。交付附逐条对账表：`方案条目 → 实现文件:行 → 验证用例 → 实测证据`。

**M6. 独立验收 + 举证制**
验收人 ≠ 实现人；验收必须附**可复核证据**（真实截图/录屏/线上可点 URL），不接受"我跑过了"。对用户交付的是**产出物**（地址/ID），不是自我声明。

**M7. CI 反假绿门**
- 静态扫描 `verify_*.cjs` / `*.mjs`：命中 `if (!env) return`、`process.exit(0)` 早退、`console.log('pass')` 之类**静默通过模式** → 告警/失败。
- 测试报告强制**三态**：`passed / failed / skipped`，skipped ≠ passed。
- 关键路径设"**必须执行清单**"，缺一即红。

**M8. 修复即回归（先红后绿）**
每个 bug 修复必须先补一条**在修复前必然为红**的断言（复现），再修到绿。杜绝"修了但没回归"。

**M9. 最小可验证闭环优先（walking skeleton）**
不先写大方案再实现；先做 **1 个端到端最小闭环**（1 个风格 × 1 个内容 × 真实链路），用真实数据验证"效果确实变了"，再铺开。**方案评审时必须同时评审"怎么证明达标"**，答不出不算方案。

### 5.3 反假绿检查清单（交付前逐项打勾）

- [ ] 每条验收断言是"差异式"，不是"存在式"
- [ ] 风格/模板测试做了 A/B 对照，且给出了可量化差异
- [ ] 本套件通过变异测试（注入缺陷 → 测试必须变红）
- [ ] 无静默跳过；skipped 已计入"未验证"
- [ ] 跑的是真实链路 E2E（真库真 theme_id），不是只调内部函数
- [ ] 方案条目全部有"实现 + 用例 + 证据"三元组
- [ ] 验收人 ≠ 实现人，证据可复核
- [ ] 修复类改动有"先红后绿"的回归断言

## 八、一页话总结

- **服务化**：先做**确定性工具层**（模板/资产/渲染/质检），再做**受控流水线**，别一上来就全自主 Agent。
- **防假绿**：把"存在性断言"换成"**差异式断言**"，用**变异测试 + 负控 + skip=fail** 证明测试真的有效，用**真实链路 E2E + 三方对账 + 举证制**证明实现真的落地。
- **根本心法**：**能证明它变好了、和以前不一样，才算交付**；"测试全绿"不等于达标。
