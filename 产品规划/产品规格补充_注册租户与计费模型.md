## 0. 背景与边界

本规格定义「谁、以什么身份、进入什么形态的租户、如何计费」，解决三件事：

1. **学校如何成为正式租户**（不自助拉起实例，由平台运营开通）。
2. **教师个体如何自助进入平台并认领学校**（不立刻造共享租户，先作个体用户 + 认领元数据）。
3. **个体教师持续使用的计费**（不掐断「养线索 → 学校转化」飞轮）。

边界约束（沿用已拍板前提）：
- SaaS 多租户 = 每校独立实例 + 独立库；私有部署是另一套账套，本规格**只覆盖 SaaS**，不涉私有部署。
- 微信扫码 / 短信验证码通道均列为 **P2**，本规格的注册流程先以「手机号 + 密码 / 邮箱 + 密码」承载，不依赖 P2 通道。
- 自主注册用户要求**手机 + 邮箱验证**；「系统设置用户」（运营端创建 / CSV 导入 / 种子）除外。

## 1. 注册与租户开通模型（双漏斗）

总体状态机：以「被认领学校是否已是租户」分流。

```
                   学校名 / 认领请求
                        │
          ┌─────────────┴─────────────┐
   学校已是租户？                      学校不是租户？
          │ 是                            │ 否
   Rule 2：教师申请加入             Rule 3：教师个体认领
   （提醒找租户管理员，               （成为个体用户 + 认领元数据
    走加入申请流程）                   + 中心聚合同校认领者）
          │                                 │
          │                         聚合达阈值 → 触发漏斗 A（销售跟进）
          │                                 │
          └──────────┬──────────────────────┘
                     │
        Rule 1：平台运营开通租户（漏斗 A）
        （含学校自主申请入口 + 知了协助 + 销售线下沟通）
```

### 1.1 漏斗 A — 学校自主申请开通（Rule 1）

- **入口**：学校可在注册页提交「开通租户申请」（学校名 / 区域 / 联系人 / 规模）。这只是一个**申请入口**，不自动建租户、不拉起实例。
- **流转**：申请进入平台运营工作台 → 运营（可由「知了」AI 代运营辅助归集信息、起草待办）→ 转**销售**做线下沟通 → 销售确认意向后**申请运营正式开通** → 运营在后台创建租户实例、写入 `School.CloudTenantID`、置 `LicenseStatus=trial/active`、配置 `TokenQuota`。

> 与「运营直接开通」不冲突：漏斗 A 是「采集信息的多请求流程」，运营开通是「执行的唯一点」。两种方式最终都收敛到运营开通动作。

### 1.2 Rule 2 — 教师申请加入已存在租户

- 教师注册时选择学校，系统查中心注册层：该校 `status=tenant`（已是租户）。
- 流程：**不新建账号**，提示「该校已有租户，请联系本校管理员加入」→ 教师提交「加入申请」（姓名 / 手机号 / 任教学科 / 班级）→ 该租户 IT 管理员在后台收到申请 → 用「运营端创建账号」能力（`POST /api/admin/users`）建号并关联。
- 术语：教师对已是租户的学校是「**申请加入**」，不是「认领」。

### 1.3 Rule 3 — 教师个体认领非租户学校（个体用户）

- 教师注册时选择学校，系统查中心注册层：该校 `status=claimed/none`（非租户）。
- 结果：教师成为**个体 SaaS 用户**（免费个人工作空间），其「学校 + 班级 + 学科」仅作为**认领归属元数据**记录在中心层（不建共享租户、不自动造管理员）。
- **多教师认领同校**：中心层聚合该校所有认领者，`班级 + 学科`用于两件事——（1）**销售线索聚合**：「X 校已 N 位老师认领、覆盖年级/学科 Y」→ 触发漏斗 A 销售跟进；（2）**防重复标记**：同一 (校,班,学科) 出现多人 → 标记待核实（可能重复注册），不阻断注册。
- 价值重定义：Rule 3 的「班级+学科排重」从「冲突解决」转为「线索信号」，更务实，也规避了「谁当管理员 / 抢注」缺陷。

### 1.4 平台运营代运营与「知了」

- 平台运营处理开通申请 / 线索时，「知了」（运营 AI）提供辅助：信息归集、草稿、待办提醒、线索汇总；**人工只在销售线下沟通环节介入**。

## 2. 个体教师计费模型（双轨）

### 2.1 核心原则

**个体教师计费不能掐断「养线索 → 学校转化」的飞轮。** 免费额度给足到「成瘾/依赖」，付费墙只拦重度使用者，并把其顺势推给销售。

### 2.2 计费单元

产品 AI 重算力，计费锚点统一为 **AI 生成额度**：
- 出题 / 教案 / 课件 / 小微对话各折算 X 额度；知识图谱、导出等为增值功能。
- 学校租户：全校额度池（`School.TokenQuota` / `TokenUsed`，代码已就绪）。
- 个体用户：个人月度额度（`usage_meters`，本规格新增）。

### 2.3 三档形态

| 形态 | 额度 | 适用 | 触发 |
|------|------|------|------|
| **免费层** | 月度上限（如 30 次 AI 生成/月） | 所有个体用户 | 注册即享，够体验「提分」价值形成依赖，封顶控成本 |
| **个人 Pro** | 更高/无限额度 + 全功能 | 学校始终不转化的长尾个体 | 免费额度用尽后二选一之一 |
| **租户 License** | 全校额度池（按席位/学年） | 学校转正后该校全体 | 学校转化后 claims 用户并入，个人计费终止 |

### 2.4 付费触发与转化切换

- 个体用户额度用尽时给**二选一**，不硬拦：① 升级个人 Pro（订阅/按量）；② 发起/加速本校租户开通（B2B，往往更划算且功能全）。
- 学校经漏斗 A 转正租户后：中心层把该校 `user_school_claims` 批量转为租户成员邀请，个体 `usage_meters` 并入 `School.TokenQuota` 池，个人计费终止。

### 2.5 架构前置

计费需中心层新增 `usage_meters`（user_id / school_registry_id / 周期 / 已用额度 / 上限 / 状态 free|pro|tenant_covered），与 `user_school_claims` 联动。详见技术方案。

## 2.6 License 分层边界（2026-07-29 补充）

本规格覆盖的是「层2 产品内订阅」（2B 学校租户成员 + 2C 个体会员），**不涉及层1 cloud license**（谁有资格运营知微实例，见技术方案 §0.5）。

- 2C 个体教师（学校永不成租户）只受本规格的会员/计费约束（`usage_meters` free/pro/tenant_covered），**不受 cloud license 约束**——cloud license 是组织/实例级授权，根本不进产品内用户层。
- 层1 cloud license 三类（自家生产 / 私有化 / 公有云 SaaS 客户集团）的模型见技术方案 §0.5；私有化客户同为订阅续期制，非买断。
- 个体教师在 school 内建模为「个人租户」（`tenant_type=personal`，席位上限=1），与 2B 学校租户共用一套多租户引擎；本规格 Rule 3 的认领/计费逻辑即作用于此形态。

## 3. 与既有规格书的关系

- 本规格的 Rule 3（个体用户归属）即 `账户系统与cloud.ziwi.cn对接方案.md` §5 待拍板 #3「B2C 个人版账户归属」的正式答复：**个体用户由 cloud IdP 统管身份，school 侧以「认领元数据 + 中心聚合」承载，不建独立 school 个人版库**。
- 计费锚点复用已有 `School.TokenQuota/TokenUsed`，个体扩展 `usage_meters`，不重复造轮子。
- 平台角色（`platform_ops/devops`）沿用该方案 §3.4：由 cloud JWT 签发携带，school 用户表不建平台账号。
