# F-2 统一鉴权错误契约 · 方案（待拍板后实现）

> 来源：`QA_从严回归_20260710.md` F-2【MEDIUM·API 契约一致性】。当前 4 套鉴权错误结构不一致，前端需为不同端点写不同解析分支，`error` 部分位置是自由文本短语（非稳定枚举），不利监控/i18n。
> 本文件为**方案**，不改运行代码；实现需前后端协同，待明确授权后执行。

## 一、现状（4 套，实测）

| 位置 | 响应结构 | 示例 |
|---|---|---|
| `middleware/cloud_auth.go` 缺头 | `{error, message}` | `{"error":"MISSING_TOKEN","message":"缺少认证信息"}` |
| `middleware/jwt_auth.go`（学校 JWTAuth）缺头 | `{error}` 仅短语 | `{"error":"missing authorization header"}` |
| `middleware/rbac.go` 越权 | `{error, message, required}` | `{"error":"INSUFFICIENT_PERMISSIONS","message":"...","required":["it_admin"]}` |
| `handler/auth_cloud.go` 云登录失败 | `{error, message}` / 部分 `{code,...}` | `{"error":"CLOUD_AUTH_FAILED","message":"..."}` |
| `handler/auth_handler.go` RefreshToken 缺头 | `{error, message}` | `{"error":"MISSING_TOKEN","message":"缺少认证信息"}` |
| `handler/school_class_handler.go` 越权 | `{error}` 自由文本 | `{"error":"只能操作自己的学校"}` |

## 二、统一目标结构

```json
{ "code": "<稳定枚举>", "message": "<可读中文>", "detail": { ...可选 } }
```

- `code`：稳定枚举（大写蛇形），前后端契约锚点，监控/告警/i18n 按 code 匹配，不依赖 message。
- `message`：可读文案，允许随版本微调，不作为程序分支依据。
- 越权类保留 `detail.required`（原有 `required` 字段语义）。

## 三、稳定枚举码表（建议）

| code | HTTP | 含义 | 替代的原 error 值 |
|---|---|---|---|
| `UNAUTHENTICATED` | 401 | 未认证/令牌缺失或无效 | `MISSING_TOKEN`、`missing authorization header` |
| `FORBIDDEN` | 403 | 已认证但无权限 | `INSUFFICIENT_PERMISSIONS`、`ROLE_NOT_FOUND`、`INVALID_ROLE_TYPE`、`只能操作自己的学校` |
| `INVALID_REQUEST` | 400 | 请求参数/字段缺失 | 各地 `INVALID_REQUEST` |
| `CLOUD_AUTH_FAILED` | 401 | 知微云凭据验证失败 | `CLOUD_AUTH_FAILED`（保留业务码，仅字段统一） |
| `PRODUCT_NOT_SUBSCRIBED` | 403 | 未订阅 school 产品 | `PRODUCT_NOT_SUBSCRIBED`（保留） |
| `CLOUD_NOT_CONFIGURED` | 503 | 云端验签未配置 | 保留 |
| `TOKEN_EXPIRED` | 401 | access token 过期 | 预留 |

## 四、实现步骤（授权后）

1. 新增 `internal/middleware/response.go`：`Unauthorized(msg, detail)` / `Forbidden(msg, detail)` / `BadRequest(msg)` 统一返回 `{code, message, detail}`。
2. 替换上述 6 处响应：`c.AbortWithStatusJSON(... gin.H{"code":..., "message":...})`。
3. 前端：统一错误解析改为读 `err.code`（不再分支 `error`/`code`），按 `UNAUTHENTICATED`→跳登录、`FORBIDDEN`→提示无权限、`INVALID_REQUEST`→字段提示。
4. staging 部署验证：原回归 C1/E1/E2/E5/E6/H1/H2 仍应 401/403，且响应体含 `code` 稳定枚举。

## 五、风险与注意

- **前端破坏性**：现有前端若依赖 `error` 字段，改 `code` 后需同步前端，否则解析失效。须前后端同版本部署。
- **迁移策略**：建议后端先全量改 `code` 并保留兼容？不推荐双字段（回归漂移）。直接前后端协同切换，staging 验证通过再谈生产。
- **不在本轮擅自改动**：属公共 API 契约变更，按纪律需明确授权后执行。
