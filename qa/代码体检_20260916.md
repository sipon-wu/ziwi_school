## 二、P0 · 会持续产生缺陷的（优先处理）

### P0-1 God Component：`CoursewareBuilder.tsx` 2,575 行

```
useState 61 · useEffect 18 · useMemo/useCallback 仅 2 · any 58 处 · exhaustive-deps 禁用 8 处
```
**为什么危险**：状态与副作用集中在一个组件里 → 任何一次改动都可能牵动无关路径；且 `useMemo` 只用 2 次，意味着**大量重渲染**。
**实证**：本轮我们修的白屏、封面缺失、班级口径三处缺陷，根因都在这个文件（`VisualBlocks`/`previewSlides` memo 依赖缺失、`index=docSlide+1`、`classLabel=gradeName`）。

**优化思路（不落地，仅方案）**
1. **按领域抽自定义 hook**（按依赖顺序）：
   - `useCwOutline`（提纲与元素层状态）
   - `useCwGenerate`（生成管道：参数装配/调用/落库/版本）
   - `useCwPreview`（整本索引 deckIdx、HD 舞台、H5 快照）
   - `useCwDecor`（装饰元件与套版）
   - `useCwSave`（保存/发布/自动保存/版本节奏）
2. **状态机收敛**：生成态 / 编辑态 / 预览态三态显式化（现散落在 `generating`、`workMode`、`previewOpen`、`cwLoading` 多个布尔里）。
3. 抽 hook 时**先补类型契约**（见 P0-3），否则只是把 `any` 搬了个家。

### P0-2 陈旧闭包：16 处 `exhaustive-deps` 禁用

分布：`CoursewareBuilder.tsx` 8、`useApi.ts` 2、`PptxPreview.tsx` 2、`LessonPlanEditor/ExerciseGenerator/ExamBuilder` 各 1。

**实证**：本轮修的 `previewSlides` memo 只依赖 `[cwOutline]`，而班级/署名是**异步随后到达** → 封面被缓存成"当时还没值"的版本 → 教师看到空信息条。这类缺陷**不会报错、只会在特定时序下错**，最难查。

**优化思路**
1. 逐条分类三档：① 补依赖即可（最安全）② 需要 `useRef` 保存最新值（回调型）③ 真需要"只在挂载时跑"（加注释说明理由 + 初始值来源）。
2. **禁止新增**禁用；CI 阶段用 lint 规则统计趋势（只减不增）。
3. 优先处理"**输入异步到达**"的那一类（班级/署名/主题/知识图谱），它们最有隐蔽性。

### P0-3 类型契约缺失：457 处 `any`

Top5：`CoursewareBuilder` 58、`SettingsPage` 40、`ExerciseGenerator` 32、`TipTapEditor` 20、`exportPptx` 19。

**优化思路**
1. **先建领域类型契约**（一次性建模，收益最大）：`CwSlide` / `OutlineSlide` / `Material` / `Facet` / `ClassInfo` / `ScopeResolved` / `H5Component`。这些在代码里都已是事实结构，只是没被命名。
2. `as any` → `as unknown as T` + 收窄函数（如我们已在做的 `asText()` / 数据消毒）。
3. **增量严格**：新文件开 `strict`、老文件白名单，逐步收紧（一次性开 `noImplicitAny` 会造成上千报错，不可行）。

### P0-4 异常被吞：前端 28 处静默 + 后端 180 处宽泛捕获

**实证**：最高危是生成链路 `CoursewareBuilder.tsx:682` `materialAPI.get(genBaseId).catch(()=>null)` —— 参照课件拉取失败被静默丢弃，教师感知不到"基线丢了"。

**优化思路**
1. 前端：统一走 `lib/api.ts:719` 的 `notifyError`（已有基础），用 **lint 规则禁止裸 `catch(()=>{})`**。
2. 后端：给 `except Exception` **分级**——
   - A 类（顶层兜底，保留）：接口边界返回 5xx 并记录；
   - B 类（业务内部，必须改造）：补上下文（哪个课件/哪个知识点/第几步）后重抛或降级并**标记**（如 `kg_store.py` 已有 `prereq_source:"error"` 的带标记做法，可作为范式）。
3. 先做"带标记的降级"而不是"静默"，我们是教学产品：教师宁可看到"这步失败了"，也不能看到"什么都没发生"。

**关键发现（类型化的额外收益）**
- `recommended_refs` 实际是 **`string[]`**（消费方 `setMaterialRefs` 是 `string[]`），此前被 `any` 掩盖 —— 若它返回非字符串，运行时才会炸。
- `textbook_version_id/name` 位于**配方壳这一层**（与 `scope_resolved` 平级），不是 `scope_resolved` 内部字段 —— 契约里已注明，避免下次读错层级。
- `LessonPlanEditor` 属性访问的 narrowing 在 `setState` 回调里会失效 → 已改为先取局部量（这类问题此前也靠 `any` 压过去）。

**度量**：`any` 457 → **453**（`tsc --noEmit` 0 错误）。
**为什么只降 4**：剩余 453 主要分布在 `SettingsPage`(40)、`ExerciseGenerator`(32)、`TipTapEditor`(20) 以及约 30 个仍为 `request<any>` 的其它端点。
**下一轮 P0-3 建议顺序**：① 其余 `request<any>` 按端点逐个补返回类型（每个都能连带消灭下游若干 `any`）② `useState<any>` 逐个按契约替代 ③ `SettingsPage`/`ExerciseGenerator` 的局部类型建模。

**类型化逼出的真实 bug（4 处，此前全靠 `any` 掩盖）**
1. 教案课标：后端给 **JSON 字符串**，却直接塞进数组 state（`LessonPlanEditor` 生成分支）→ 已改为 parse + try/catch。
2. 教案 `period` 可能返回字符串 `"2"` → 后续算术会错 → 已 `Number()` 收敛。
3. `knowledge_node_ids` 可能直接是数组，原代码无脑 `JSON.parse` 会抛错 → 已按类型分支处理。
4. 排重接口返回的 `duplicates` 可能缺省 → `Object.values(undefined)` 会炸 → 已 `|| {}`。
   另修两处"属性访问 narrowing 在 setState 回调里失效"、一处 `setExam(undefined)` 应为 `null`。

**类型化逼出的真实契约（此前无人知道）**
- 生成响应有 `divergence_map` / `similar_material` / `recommended_materials` 三个字段。
- `recommended_refs`、`material_refs` 实际是 `string[]`（消费方是 `string[]`）。
- `textbook_version_id/name` 在**配方壳这一层**，不是 `scope_resolved` 内部。
- 部分接口会把 body 再包一层 `{ data }`（调用点的 `?.id || ?.data?.id` 是合理防御）。
- 教材静态数据是**三层索引** `[版本][年级][学期]`；单元对象为 `{ unit, kps }`。
- 接口存在两种时长字段：`duration` 与 `duration_minutes`；题面 `stem` 与 `content` 并存。
