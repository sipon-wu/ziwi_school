# 课件生成 Skills 架构方案

> 定位：**替代手搓**的可扩展课件生产方案
> 核心判断：课件生成能力必须由 **Skill（能力包）** 承载，而非硬编码；Skill 需**可插拔、可替换**，
> 并统一归口到**小微**的能力体系，对用户透明。
> 状态：方案阶段；先在 CodeBuddy 会话内用种子数据试验，再平台化。

---

## 一、为什么必须是 Skills（而非手搓）

本次《观潮》的手搓实践暴露了硬编码路线的根本缺陷：

| 问题 | 表现 |
|------|------|
| 质量不可控 | 反复 6 轮调字号/布局，仍在"差感觉"层面打转 |
| 不可扩展 | 12 套课件已耗尽大量工时，无法覆盖全部学科×年级 |
| 修改成本极高 | 改一个装饰要 build + deploy + 验证（约 15 分钟/次） |
| 无法赋能用户 | 教师想生成自己的课件时，没有可用链路 |
| 知识不可复用 | 排版经验、质检标准散落在代码和对话里 |

**结论**：课件是"内容产品"，不是"代码产物"。内容产品应由**内容流水线**生产，
流水线能力封装为 **Skill**，才能复用、升级、赋能用户。

## 二、Skills 架构总览

```
                     用户（教师）
                          │  "帮我生成《观潮》课件"
                          ▼
              ┌───────────────────────┐
              │   小微（统一入口）      │  ← 用户只感知小微
              │   · 意图识别           │
              │   · 能力编排           │
              │   · 结果呈现           │
              └───────────┬───────────┘
                          │ 意图：courseware.generate
                          ▼
              ┌───────────────────────┐
              │   Skill Registry      │  ← 注册中心（可插拔的关键）
              │   注册 / 发现 / 版本    │
              └───────────┬───────────┘
                          │ 匹配 → 动态加载
                          ▼
        ┌─────────────────────────────────────┐
        │      课件生成 Skill（可替换）         │
        │  ┌───────────────────────────────┐  │
        │  │ sop:    S1→S2→S3→S4→S5        │  │
        │  │ tools:  模板查询/素材检索/渲染  │  │
        │  │ quality: 三道质检关卡          │  │
        │  └───────────────────────────────┘  │
        │  当前实现：pptx skill v1             │
        │  未来替换：更强的 skill v2（零改动）  │
        └─────────────────┬───────────────────┘
                          │
                          ▼
              百炼（模型层：LLM 能力）
```

### 四层机制（回答"平台如何自动加载"）

#### ① Skill 定义（标准化清单）
每个 Skill 声明"我是谁、能做什么、怎么做、做到什么标准"：

```yaml
id: courseware.generate
name: 课件生成
version: 1.0.0
intent: 用户要求生成 / 修改 / 优化课件
triggers: ["生成课件", "做个PPT", "课件", "帮我出课件"]
input:
  - source: 教案ID | 主题 | 学段学科 | 课时
  - style_hint: 期望风格（可选）
output:
  format: 课件内容（Markdown + VISUAL 组件 + 素材引用）
  deliverables: [平台课件, PPTX, PDF, H5]
sop:
  - S0 需求澄清（校验生成条件，缺失则提问补全）★ 课标对齐守门
  - S1 教案解析
  - S2 提示词生成（小微）
  - S3 课件生成
  - S4 质量检验（三关）
  - S5 交付入库
tools:
  - template.query      # 按风格/学科/学段查模板
  - asset.search        # 素材检索
  - slide.render        # 页面渲染
  - visual.check        # 视觉检查（转图 + subagent）
quality:
  gates: [自动规则, AI评审, 视觉检查]
  pass_criteria: 关卡1全过；关卡2各项≥4分；关卡3无阻塞问题
```

#### ② Skill Registry（注册中心）
平台维护 Skill 注册表，是"可插拔"的支点：

| 字段 | 作用 |
|------|------|
| `id` | 唯一标识 |
| `version` | 版本号（支持并存、灰度） |
| `intent / triggers` | 意图匹配依据 |
| `status` | active / deprecated / testing |
| `entry` | 执行入口（提示词模板 / 服务 / 脚本） |
| `quality_gates` | 该 skill 的质检标准 |

**替换 Skill = 注册表里加一条新版本 + 切换 status**，调用方零改动。

#### ③ 意图路由（自动加载的核心）
```
用户输入
  → 小微做意图识别（LLM + 规则）
  → 得到 intent（如 courseware.generate）
  → Registry 按 intent 匹配候选 Skill（可多个）
  → 按 version / status / 场景评分选最优
  → 动态加载其 sop + tools + quality
  → 执行
```

用户全程只说"我要课件"，**不感知底层是哪个 Skill、什么版本**——即"统一归在小微能力里"。

#### ④ 执行引擎
- **百炼**：提供 LLM 能力（提示词生成、内容生成、评审）
- **Skill**：提供 SOP、领域知识、质检标准
- **小微**：编排调度、状态管理、结果呈现、用户互动

**模型升级与 Skill 升级解耦**：百炼换更强模型 ≠ 改 Skill；Skill 换更优 SOP ≠ 动模型。

## 三、Skill 统一接口（保证可插拔）

所有课件生成类 Skill 实现同一接口，替换时不影响小微：

```
interface CoursewareSkill {
  match(intent, context): number        // 匹配置信度 0-1
  plan(input): Plan                     // 产出执行计划（页面规划/组件/素材）
  execute(plan, tools): Draft           // 生成课件草稿
  verify(draft, gates): QualityReport   // 跑质检关卡
  revise(draft, issues): Draft          // 按问题修订（支持多轮）
}
```

**替换示例**：
- v1：基于模板 + 规则生成
- v2：引入多模态素材理解、更优排版模型
- 替换动作：注册 v2 → 灰度 10% → 全量 → 下线 v1
- 小微代码：**零改动**

## 四、课件生成流程（Skill 内部的 SOP）

（详细流程见 `课件生成流程方案.md`，此处只列与 Skill 的衔接）

| 阶段 | Skill 内部动作 | 依赖能力 |
|------|---------------|---------|
| **S0 需求澄清** | 校验生成条件；缺失则提问；无教案时从知识点/课标库推断 | 意图识别 + 知识点库 + 课标库 + 多轮对话 |
| S1 教案解析 | 解析 LessonPlan → 结构化 JSON | 规则解析 + LLM 补全 |
| S2 提示词生成 | 教案 + 宪法 → 生成提示词 | 百炼 LLM |
| S3 课件生成 | 提示词 → 页面 + 组件 + 素材 | 模板查询 / 素材检索 / 渲染 |
| S4 质量检验 | 三道关卡（规则 / AI评审 / 视觉） | visual.check（转图 + subagent） |
| S5 交付入库 | 入库 + 绑定来源 + 可导出 | materials 写入 |

> **S0 是课标对齐的守门环节**：用户未必有教案，若不问清学科/年级/课题就生成，
> 会出现"内容像样但课标不对齐"。无教案时仍可经知识点库/课标库推断并请用户确认。

**Skill 的关键价值**：把"宪法"（生成规范）、"组件选型规则"、"质检标准"这些**领域知识**
固化在 Skill 里，而不是散落在代码或对话中。

## 五、当前会话的试验计划（阶段一）

**目的**：用种子课件数据验证"Skill 介入生成"的可行性，不追求完美。

| 步骤 | 动作 | 产出 | 验证标准 |
|------|------|------|---------|
| T1 | 确定试验样本：种子课件 12 套（或先取 2-3 套） | 样本清单 | — |
| T2 | 为样本准备教案（AI 生成或现有教案） | 教案结构 JSON | 通过 S1-QC |
| T3 | 小微依教案生成提示词 | 生成提示词 | 通过 S2-QC（目标全覆盖、页数匹配） |
| T4 | **pptx skill 按提示词生成课件** | 课件内容（MD + VISUAL） | 通过 S3-QC |
| T5 | 跑质检三关（含 subagent 视觉检查） | 质检报告 | 关卡1全过；关卡2≥4分；关卡3无阻塞 |
| T6 | 入库 + 浏览器验收 | 可编辑、可导出的课件 | 与手搓版对比质量 |

**与手搓版的关键对比指标**：

| 指标 | 手搓版 | Skill 生成版（预期） |
|------|--------|---------------------|
| 单套耗时 | 数小时 | 分钟级 |
| 质量稳定性 | 依赖人工反复调 | 依赖质检关卡，可控 |
| 可扩展套数 | 有限 | 无上限 |
| 用户可自助生成 | ❌ | ✅ |

## 六、平台化路径（阶段二）

| 能力 | 实现 | 说明 |
|------|------|------|
| Skill 注册中心 | 后端表 / 配置服务 | 存 id/version/intent/status/entry |
| 意图路由 | 小微内 LLM 意图识别 + 规则兜底 | 匹配 Skill |
| Skill 执行 | 百炼 LLM + 平台工具（模板/素材/渲染） | Skill 调 tools |
| 用户互动 | 小微对话式：用户提需求 → 调整提示词 → 重新生成 | "多加互动""讲细一点" |
| 质量内建 | 生成后自动出质检报告，用户可见 | 关卡1/2/3 结果 |
| 可插拔替换 | Registry 版本管理 + 灰度 | 升级不影响用户 |

**用户体验**（始终归口小微）：
```
教师：小微，帮我生成《观潮》的课件，30分钟课时
小微：好的，我先看下教案…已生成 14 页课件，质检通过。
      [预览] [调整：多加互动] [导出PPTX]
教师：多加些互动
小微：已重新生成，互动环节从 2 处增加到 4 处。
```

## 七、关键设计决策

| 决策 | 理由 | 风险与对策 |
|------|------|-----------|
| Skill 承载生成能力 | 可复用、可升级、可赋能用户 | Skill 设计不当 → 质量差；对策：强质检关卡 |
| 统一归口小微 | 用户无需理解底层 | 意图识别错误；对策：规则兜底 + 用户可指定 |
| 可插拔替换 | 随时用更强能力 | 版本兼容；对策：统一接口 + 灰度切换 |
| 百炼与 Skill 解耦 | 模型升级与方法论升级独立 | — |
| 先试验后平台化 | 降低风险 | — |

## 八、Skill 能力边界与输出契约

> 2026-08-31 补充。此前对"Skill 需要被约束什么"存在误判，经实际探针验证后修正。

### 8.1 我们只供给两样：要求 + 素材

| 我们供给 | Skill 负责 |
|---|---|
| 教学性要求（学生视角 / 课标对齐 / 互动≥2处 / 教学评一致） | 组织内容、设计环节 |
| 风格提示词语义（见《风格提示词库方案》） | 决定配色、字号、版式 |
| 素材库（版式库 / 装饰资产 / 学科组件） | 选用并给出参数 |
| 输出契约（结构化 + 资产引用） | 按契约产出 |

**Skill 不负责现造素材**——素材已存库，只需引用。

### 8.2 Skill 自带能力：不要重复约束

探针验证确认，成熟 PPT Skill 自带完整视觉规范：

| 能力 | Skill 自带 |
|---|---|
| 字号阶梯 | 标题 36-44pt / 小节 20-24pt / 正文 14-16pt / 注释 10-12pt |
| 间距留白 | 边距 ≥0.5"、块间距 0.3-0.5"、必须留白 |
| 配色 | 多套主题调色板 |
| 版式库 | 双栏 / 图标行 / 2×3 网格 / 半出血图 |
| 错误清单 | 15 条 Avoid 规则（含"禁止标题下加装饰线"） |

**我们曾反复打磨的「字密」「表格空列」「版式单调」，Skill 天然不存在。**

教训（写入执行约定）：**先探测 Skill 能力，再决定约束什么；不要预设它不行。**
用"限制字数"去迁就糟糕的容器结构，是方向性错误——正确解法是换容器结构（分层呈现），不是限制内容。

### 8.3 输出契约：结构化内容 + 资产引用

Skill 产出**内容与结构决策**，不是成品文件：

```json
{
  "styleDNA": { "colors": { "primary": "...", "accent": "..." }, "density": "normal" },
  "slides": [
    { "title": "三种表示法对比", "layout": "content-2col", "bullets": ["..."] }
  ],
  "decor_refs": [
    { "asset_id": "leaf-cluster", "tone": "accent", "params": { "count": 3, "scale": 1.2 } }
  ]
}
```

**硬性约束**：装饰引用中**不得出现色值**，只能写语义槽（主色 / 强调色 / 弱化色）。
具体颜色由 Skill 当次生成决定，并随 `styleDNA` **快照进课件**。

文件生成（.pptx/.pdf/H5）由底层现成能力在最后环节完成，不污染内容层。

### 8.4 引用而非生成（省 token）

| 方式 | 每处成本 |
|---|---|
| Skill 现造装饰图形 | ~500 tokens |
| 引用资产 ID | ~30 tokens |

一份课件 16 处装饰：现造 ~8000 tokens，引用 ~500 tokens，**差约 16 倍**。
且引用版天然风格统一、可校准——用户反馈能反哺资产默认参数，让所有后续课件受益。
