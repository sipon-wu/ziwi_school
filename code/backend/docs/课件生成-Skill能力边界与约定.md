# Skill 能力边界与提前约定

> 来源：2026-09-01 用 `qwen-plus` 批量生成 7 套种子课件的**实测记录**。
> 目的：回答"Skill 哪些做得到、哪些做不到"——做不到的要么写进提示词提前约定，
> 要么由平台兜底，不要指望 Skill 自己悟。

---

## 一、机制（已落地）

```
提示词（skills/ 单一事实源）
   ↓ 生成
模型产出最终 Markdown
   ↓ 编码（VISUAL base64）+ 白名单清洗（平台兜底，非内容决策）
   ↓ S4 关卡1 自动规则校验  scripts/check_courseware_quality.py
   ↓ 未过 → 把违规清单 + 被丢弃物 + 上一版原稿 回灌提示词（限次）
   ↓ 保留违规最少的一版
产物
```

两个脚本：

| 脚本 | 职责 |
|---|---|
| `scripts/generate_seed_coursewares.py` | 生成 + S4 重试闭环（规则从 `skills/` 加载） |
| `scripts/check_courseware_quality.py` | 只读校验，判据来自质量宪法与版式选型 |

## 二、实测效果

| 轮次 | 违规数（7 套合计） | 单套**首轮**违规 | 关键改动 |
|---|---|---|---|
| 首轮 | **116** | ~13 | 仅靠提示词描述规则 |
| 二轮 | 30 | ~9 | 输出契约 + 交卷前自检清单 |
| 三轮 | 8 | ~9 | 重试时附上原稿，让 Skill **修订**而非重摇 |
| 四轮 | 10 | **~3** | 字数分拆示范 + 字段结构示例（写进 skills/） |
| 五轮 | **7** | ~3 | 套路拆分：PPT / H5 各有页面结构 + 英文换算 |

> 三四轮**总量**接近（8 vs 10，属正常波动），但**首轮**违规从 ~9 降到 ~3——
> 这才是关键：更少的第一轮错误 = 更少的重试 = 更省 token。
> 用户原则：「PPT 提示词要提前考虑字数分拆」——**事前预防优于事后重试**。

末轮分布：繁星 0、观潮 1、走月亮 1、桂花雨 1、My School 2、天气 2、函数 3。

## 三、有效的提前约定（实测验证过）

按贡献从大到小：

1. **字段结构示例**（不是字段说明）—— 首轮违规 9 → 3，贡献最大。
   选型文档写了"compare-table rows 2~5 行"，但 Skill 仍交出二维 `cells`
   （对它更直觉，但前端只认 `rows` 嵌套）→ 渲染成空表。
   给出完整 JSON 示例后立刻写对。
   *字段说明 ≠ 字段结构，模型需要看到嵌套长什么样。*

2. **字数分拆示范**（写进 `skills/` 领域知识，不写进脚本）——
   同一句原文给出三种处理：拆成 grid（每条 ≤12）/ 拆成 2col（≤30）/
   拆不动就整块走 annotate。
   *这正是"提前考虑"：动笔前拆句，比写完被判违规再返工省一整轮。*

3. **输出模板里示范一个互动页** —— 决定性的一条。
   只在文字里描述"互动写 `<!-- quiz: -->`"时，Skill 交出 **0 处互动**；
   模板里放了一个完整互动页后，稳定产出 5~8 处。
   *模型对"照着抄"的遵守度远高于"照着描述做"。*

4. **重试时附上原稿让 Skill 修订** —— 违规 30 → 8。
   只给违规清单会让它推倒重写，已合规的页面被重新摇一遍引入新违规
   （实测出现过 10 → 5 → **9** 的反弹）。

5. **把"被丢弃的东西"回灌** —— 光说"互动 0 处"Skill 改不对，
   必须告诉它"你写的 `type:quiz` 不是合法组件、已被丢弃"，它才知道往哪改。

6. **交卷前自检清单**（针对高频违规逐条列）—— 116 → 30。

7. **注释白名单**（layout/VISUAL_JSON/read/readalong/quiz/reveal/draw）——
   根治"自创注释显示在页面上"的事故。

8. **保留违规最少的一版** —— 重试不保证单调变好，取最后一次等于听天由命。

9. **quiz 答案位置要打散**（写进契约 + 校验器）——
   Skill 默认把正确答案都放在第 2 项，实测连续 5 道都是 `| 1`。
   学生发现规律就不用思考了。提示词明确"打散"后变成 3 个 `| 1` + 3 个 `| 2`。

## 四、Skill 的能力边界（实测守不住的约束）

这些**提示词里已经写了规则**（来自 `版式与组件选型.md`），Skill 仍会犯：

| 约束 | 实际表现 | 状态 |
|---|---|---|
| annotate 装短句 | `text` 只有 18~26 字（要求 30~180），拿 annotate 装作业要求 | 未解决 |
| compare-table 结构写错 | 交二维 `cells` 而非 `rows` 嵌套 | **已解决**：给 JSON 示例后写对 |
| 空壳组件 | `rows: []` / `items: []` / `label: None`，渲染成空表或"None" | 已由兜底丢弃，回灌后改善 |
| annotate 关键词杜撰 | marks 不在 text 中真实出现 | 未解决 |
| structure 层数 / 项数 | 给 1 层或每层 1 项（要求 2~4 层、每层 2~6 项） | 提示词约束后大幅改善 |
| 组件类型当版式 | `layout: timeline` / `compare-card` | 偶发 |
| 装饰素材 ID 当组件 type | `type: eye` / `clock` | 已由白名单兜底 |
| **字数超标** | content-grid 出现 13~36 字 | **基本解决**：字数分拆示范后近乎消失 |

> 规律一：**Skill 对"字数上限"遵守得好，对"数量下限"遵守得差**。
> 超标它会拆句（有示范就会照做），不足要它**创作内容**，它就少写或留空。
>
> 规律二：**"不知道结构"和"不愿意填满"是两回事**。
> 前者给个示例就解决（compare-table 从 2 处降到 0），后者是能力问题。

**判断**：前三条属于"填不满"，本质是 Skill 对**数量下限**的遵守弱于对**字数上限**的遵守。
字数超标它能改（拆句即可），数量不足要它**创作内容**，它倾向于少写。

**可选的后续对策**（未实施，供决策）：
- 把"填不满"的组件在提示词里改成"**宁可不放，也不放半截**"——半截表比没表更糟
- 或对数量类约束，在校验失败时给出**具体补全指令**（如"这一页 compare-table 需要补 2 行 rows"）

## 五、必须由平台兜底的（Skill 做不到，不是它的问题）

| 事项 | 原因 |
|---|---|
| VISUAL 的 base64 编码 | 模型无法输出 base64，而前端 VISUAL 注释要求 base64。纯编码，非内容决策 |
| 注释白名单清洗 | 前端只认 7 种注释，白名单外的**必然**显示成乱码。删掉是保护用户 |
| 非法组件 type 丢弃 | `type` 不在 11 种内，前端渲染不出东西 |
| 空壳组件丢弃 | `rows: []` / `label: None` 会渲染成空表或字面量"None"，比不放组件更糟 |

> 这三条的共同点：都是"平台事实"导致的格式处理，不含任何内容决策。
> 判定标准很简单——**如果要替它挑内容，就是越界；如果只是让它别显示成乱码，就是兜底。**

## 六、教训（防止重犯）

1. **不要只查表面指标就宣布达标**。
   首轮我只统计了"页数 / 版式数 / 注释白名单"，就报告"7 套全部达标"；
   实际上按质量宪法逐条校验有 **116 处违规**。
   指标选错了，达标就是幻觉。

2. **不要把新注释写进 markdown**。
   `STYLEDNA` / `DECOR` 因前端不识别而原样显示在页面上。
   承载数据要用数据库字段（`color_root` / `decor_facets`），不是 markdown 注释。

## 七、提示词的套路结构（通用骨架 + 专属差异）

PPT 与 H5 是两套产物形态，但提示词共用一套骨架。规则全部落在 `skills/`，
脚本只按格式**组装**，不内置任何规则副本。

```
skills/shared/                    通用骨架（两个 Skill 共用）
├── 质量宪法.md                   内容质量：视角 / 篇幅 / 互动 / 占位符
├── 输出契约.md                   分段方式 / 注释白名单 / 互动标记 / meta / 通用禁忌
└── 字数分拆.md                   拆句手法 + 字长上限（按格式与语种分列）

skills/courseware-ppt/references/
└── 版式与组件选型.md             PPT 专属：版式集合、组件×形态、字段字数契约

skills/courseware-h5/references/
└── 场景与互动规范.md             H5 专属：scene、气泡、互动九种、学段差异

生成脚本
└── page_structure(fmt)           页面结构（决定产物形态，必须按格式给）
```

### 为什么要拆

| | PPT | H5 |
|---|---|---|
| 页面单位 | slide（bullets + VISUAL 组件） | scene（旁白 + 角色气泡） |
| `layout` | 10 种受控版式 | **只能 scene**（两者互斥） |
| 字数 | 每页 ≤120 字 | 每场景 ≤60 字 |
| 可视化 | `VISUAL_JSON` 组件（11 种） | 无（靠对话与互动推进） |
| 结构 | 含学习目标 / 小结 / 作业 | 情境线，**禁止**这些页 |
| 数量 | 12~15 页 | 8~16 场景 |

> 重演过的历史教训：拿 PPT 契约生成 H5，产出 14 页 + bullets + 9 个 VISUAL、
> **0 个 scene**——"PPT 化的 H5"。拆出各自页面结构后变成
> 16 个 scene + 0 VISUAL + 15 处互动，首轮即过。

### 参数化：骨架固定，数字按维度取

| 维度 | 取值 | 影响的数字 |
|---|---|---|
| 格式 | ppt / h5 | 页数、每页字数、有无 VISUAL、layout 集合 |
| 语种 | 中文 / 英文 | 字数标准（英文按单词计，约为中文的一半） |

英文换算（`shared/字数分拆.md`）：标题 2~8 词、grid 每条 ≤6 词、
annotate 15~90 词、每页正文 ≤60 词。

> **校验器必须用同一套换算**，否则提示词说"15~90 词"、校验器按"30~180 字"判，
> 等于又退化成两套标准，Skill 怎么改都过不了。

### H5 的缺省要求：屏幕适配

详见 `courseware-h5/references/场景与互动规范.md` 第六节。要点：

- 缺省目标：**宽窄两个比例都自适应**；做不到就**按手机窄屏设计**
- 内容侧按窄屏取上限：每场景 ≤60 字 / 气泡每条 ≤20 字 / quiz 每个选项 ≤12 字
- 宁可分两个场景，也不要一个场景塞到需要下滑

> **这条是提要求，不是查渲染器实现得出的结论。**
> 渲染器内部怎么适配、是否滚动、是否裁剪，是实现方的事——
> 提示词里只写"要什么"，不写"渲染器现在怎么做的"，
> 否则渲染器一改，这份提示词就成了错的。

## 八、校验器自身的坑（要拿产出反向验证它）

3. **校验器自身也会误报**，要拿产出反向验证它：
   - 裸的「略」把"可省略"判成占位符
   - 英文按字符数算，把 "Let's Meet the Weather" 判成 23 字（应按单词计）
   - `annotate.marks` 用 `{start, end, text}` 格式时按字符串算长度
   - 互动页被要求挂 visual（互动本身就是这页的可视化）
