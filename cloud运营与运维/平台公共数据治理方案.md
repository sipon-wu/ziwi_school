# 平台公共数据治理方案（school 产品线 1-0 公共数据 cloud 托管 + 同源下发/快照）

> 版本：v0.3（层级模型校准稿）｜日期：2026-08-09
> 状态：待用户拍板立项
> 存放：本文件位于 `cloud运营与运维/` 目录，作为 **school 产品线（1 轴）公共数据 `1-0`** 的治理基线。

> **层级模型（用户 2026-08-09 最终校准）——两套正交编号轴**：
>
> **0 轴 = 平台级公共（跨产品线，cloud 底座能力，不属于任何产品线）**
> - `0-1` heartbeat（心跳/存活监测，跨产品线平台运维）
> - `0-2` Token 供方管理（采购算力，如百炼；配额/账单/路由，跨产品线基础设施）
> - `0-3` 统一身份（IdP / 租户 / License，跨产品线身份底座）
>
> **1 / 2 / 3 轴 = 各产品线（进入产品线后，才有它自己的公共数据节点 `*-0`）**
> - `1` school 产品线 → **`1-0` = school 产品线公共数据**（课标 / 教材版本 / 知识图谱 / 蒸馏素材 / 标准模板 / 全国 K12 学校目录）
> - `2` mfg 产品线 → `2-0` = mfg 产品线公共数据（如有，例：用例数据）
> - `3` 审计产品线 → `3-0` = 审计产品线公共数据（预留）
>
> **关键区分（本次根治的核心）**：
> - `0-*` 是**平台级、跨产品线**能力，归 cloud 底座，不属于任何产品线。
> - `1-0 / 2-0 / 3-0` 是**各产品线自己的公共数据**，归属对应产品线，**不跨产品线共享**；但它们统一由 **cloud 运营平面托管与维护**（即"放在 cloud 里各产品线的名下"）。
> - 因此：**课标/教材版本/知识图谱/蒸馏素材/标准模板/全国 K12 学校目录，是 `1-0`（school 产品线公共数据），不是平台级 0 层数据**。之前误把它们写成"0-1 平台公共数据"是错误的。
> - school 业务库里现有的 `tb_textbook_version` / `tb_standard_clause` / `tb_kg_*` / `tb_lesson_source` / 全国学校目录表等"公共初始化数据"，就是这个 `1-0` 的**现状承载表**（不是平台源、也不是别的产品的数据）。
>
> **按产品线进入（设计意图）**：运营人员 / Agent / 他们的「知了」助手，进入 school 产品线只看 `1-*` 知识体系，进入 mfg 只看 `2-*`，边界分明。这样不会把 school 的课标数据误当成平台公共数据去碰，也不会跨产品线串数据。
>
> **依据（已拍板，不可违背）**：
> - 教材版本三层模型 B 版（2026-07-09）：公共初始数据平台统一维护（权威源 `tb_textbook_version`）；学校可写本地覆盖层 `school_textbook_override`（仅本校生效，不影响公共库）；上报平台审核暂缓（P2+）
> - SaaS 分水岭规则（2026-07-18）：SaaS 多租户原文永不上服务器，`storage_mode='distilled_only'`；单租户私有化可随包部署授权版本原文，`storage_mode='private_original'`
> - 私有化 license（2026-07-29）：私有化部署数据不出校、续期制（非买断）、cloud 签发带签名+有效期 license key，实例内置 cloud 公钥本地验签（离线可用）
> - 统一身份方案（2026-07-28）：cloud 统一承载租户管理账号 / 平台管理账号；产品线业务用户（teacher/student…）不进 cloud
> - 本次根治教训（2026-08-08）：公共数据曾不在代码管线、staging/prod 各自手工灌 → 环境漂移 → 测试全绿却线上无检索素材（假绿）；根治 = 代码内建建表 + 回归断言 + 数据同源

## TL;DR · 决策摘要（放最前，供评审速览）

**一句话结论**：用户直觉方向正确——把 **school 产品线公共数据（`1-0`）** 的"单一事实源"收归 **cloud 运营平面里 school 产品线下**集中托管（版本化下发），能根治"多环境手工灌导致漂移/假绿"，且天然覆盖 school 的两类消费方（SaaS 实例 + 私有化实例）。

**三个不可动摇的铁律**：
1. **分类铁律**：`1-0` school 产品线公共数据归 cloud 里 school 产品线下托管；租户/学校覆盖与业务运行数据永不进 `1-0`。
2. **分水岭铁律（按部署形态判定，不按"是否个人"）**：公有云 SaaS（无论 2B 教育局/集团还是 2C 个人）一律 `distilled_only`、**永无原文**；唯一例外是私有化 `private_original`。
3. **同源铁律**：school 的所有环境（staging / prod / 各私有化实例）从同一 `1-0` 源拉取，消除手工 seed 漂移。

**不是什么**：不是"把表挪到 cloud 库当平台数据"，而是**在 cloud 运营平面里为 school 产品线建一处托管其 `1-0` 公共数据 + 版本化下发机制**（P2 量级子系统），挂在 cloud 的 **school 产品线（1 轴）** 下。

**边界（重点）**：`0-*` 平台能力（heartbeat / Token供方 / 统一身份）与 `1-0` 产品线公共数据**性质不同、互不重叠**。本方案只动 **`1-0`**；mfg 的 `2-0`、审计的 `3-0` 同理各自在 cloud 产品线下托管，本方案不碰、不画"跨产品线下发"箭头。

**落地节奏（建议）**：先立项 → M0 cloud 里 school 产品线下 `1-0` 源表 + 抽现状 seed 为 v1 → M1 `pull` API + 鉴权分片增量 → M2 school 端快照拉取 + 双读过渡 → M3 运营 UI + 灰度/回滚/审计 → M4 私有化 license 拉快照改造 → 最后退役手工 seed。

**关键风险（高危）**：非个人公有租户（教育局/集团）易被误当"机构特例"放宽原文——**错**。分水岭按部署形态判定，公有云 SaaS 一律无原文（见 §1 铁律与 R7）。

## 0. 问题陈述

当前 school 的"产品线公共数据（`1-0`）"都**直接写在 school 业务库**，由"数据团队出 JSON 包 + 开发手动 `cmd/seed/*` TRUNCATE 重灌"维护，cloud 端完全不碰这些数据——而 cloud 早已是本应托管它的运营平面（只是 school 这条产品线的 `1-0` 节点一直没在 cloud 里建起来，退化成了各环境手工灌）。

痛点（已实证）：
1. **环境漂移**：staging / prod 各灌一份，不同步就出现"prod 建不出表 / 缺数据"而业务测试全绿（2026-08-08 假绿根因）。
2. **维护黑箱**：数据源在谁的机器、哪个 JSON、何时更新，无版本、无审计、无下发记录。
3. **私有化断链**：私有化实例的 `1-0` 数据随私有化包手工进客户机房，cloud 无从知晓、无法统一升级。

核心命题：把 **school 产品线公共数据（`1-0`）** 的"单一事实源（single source of truth）"收归 **cloud 运营平面里 school 产品线下**，通过**版本化下发**供给 school 的 SaaS 与私有化两类实例。

### 0.5 现状证据与基线（已代码/实测核实）

**A. 现有 `1-0` school 公共数据手工 seed 脚本（漂移根因的具体载体）**：
- `code/backend/cmd/seed/knowledge/main.go` — TRUNCATE 并重灌 `tb_standard_clause` / `tb_kg_node` / `tb_kg_edge` / `tb_version_standard_map`（注释明写"可重跑：启动先 TRUNCATE 5 张 tb_* 表"，即环境间各自重灌 → 天然漂移源）。
- `code/backend/cmd/seed/textbook_versions/main.go` — 独立重灌 `tb_textbook_version`。
- 蒸馏底座由 `code/backend/cmd/server/main.go` 的 `ensureDistillSchema(db)`（定义行 477，调用行 122）**幂等原生 SQL 建表**（分区表 + `vector(1024)` + HNSW，绕过 GORM AutoMigrate）；实际数据靠 `code/ai-service/scripts/ingest_lesson_source.py` + `sync_distilled.py`（按 `saas`/`private` 两 mode 走分水岭）手工同步。

**B. 分水岭的代码佐证**（`code/backend/internal/model/lesson_source.go:13` 注释）：
> "SaaS 模式 storage_mode 恒为 'distilled_only'（原文不上服务器，见分水岭规则）。"
> `tb_lesson_source` 是 32 分区表，struct 中**无原文列**，只有 `content`（蒸馏结果）、`std_clauses`、`kg_unit`、`lecture_id`、`storage_mode` 等。证实了"cloud 源与 SaaS 实例都只存 distilled"的架构约束。

**C. 2026-08-08 实测基线（staging / prod 双环境 pg 容器 `docker exec` 断言结果）**：
- `tb_lesson_source`：≥ 50000 行（实际约 58138）；`tb_lesson_lecture`：≥ 200 行（实际约 299）。
- 外键悬空（`lecture_id` 指向不存在 lecture）= 0。
- 结论：数据本身已就绪，但**维护链路不在代码管线、靠手工灌 + 游离种子进程**，正是漂移/假绿温床。本方案 §6.6 的断言脚本即把该次实测固化为 CVM cron 在线守门。

## 1. 数据分类边界（school 产品线公共数据 / 租户覆盖 / 业务运行）

必须先把"哪些进 `1-0`"划清，否则方案会无限膨胀。

| 类别 | 定义 | 例子 | 维护方 | 存储位置 |
|------|------|------|--------|----------|
| **`1-0` school 产品线公共数据（产品线权威源）** | school 产品线唯一、全租户共享同一份、随教学指南/技术动态升级；由 cloud 运营平面里 **school 产品线下**集中维护、版本化下发 | 课标条款 `tb_standard_clause`、教材版本目录 `tb_textbook_version`、知识图谱 `tb_kg_*`、蒸馏素材底料 `tb_lesson_source`/`tb_lesson_lecture`、平台标准模板、全国 K12 学校目录 | **cloud 运营平面 · school 产品线（数据团队维护，版本化）** | cloud 里 school 产品线下源库（`1-0`）+ 下发快照给 school 各实例 |
| **租户/学校本地覆盖** | 绑定具体租户，对 `1-0` 做本地化覆盖，不回灌产品线公共源 | 学校教材覆盖 `school_textbook_override`、校区结构、学校自用模板偏好 | **school 端**（学校 IT 管理员在线编辑） | school 本地库 |
| **业务运行数据** | 师生家长、教案、出题、学情等日常产出 | User / LessonPlan / Exercise / Coverage… | school 产品线 | school 本地库（SaaS 云端 / 私有化客户机房） |

> **⚠ 关键区分（澄清 `1-0` school 公共数据 ≠ 平台 0 层数据）**：
> - **`1-0` school 产品线公共数据**：归属 school 产品线、由 cloud 托管，但**不跨产品线**，mfg/审计不共享它。本方案的核心对象。
> - **school 业务库里现有的 `tb_textbook_version` / `tb_standard_clause` / `tb_kg_*` / `tb_lesson_source` / 全国学校目录表等"公共初始化数据"**：就是 `1-0` 的**现状承载表**（它们本就是 school 的，不是平台源、也不是别的产品的数据）。
> - **school 初始化时本地产生的校区/班级/学科设置、`school_textbook_override` 等**：属于本地覆盖/业务运行数据，**既不进 `1-0`，也不是平台 0 层数据**，永远留 school，不进 cloud 的 school 产品线下源。

**铁律**：`1-0` school 产品线公共数据归 cloud 里 school 产品线下托管 + 下发；租户覆盖与业务运行数据永不进 `1-0`（与统一身份方案「业务用户不进 cloud」边界一致）。
**模板细分**：平台提供的**标准模板**属 `1-0`（cloud 里 school 产品线下维护）；学校**自建模板**属本地覆盖（留 school）。
**层数归属**：`1-0` school 产品线公共数据 = **1-0**；heartbeat = **0-1 平台级**；Token 供方 = **0-2 平台级**；统一身份 = **0-3 平台级**。mfg/mfg 的 `2-0`、审计的 `3-0` 各自在 cloud 产品线下托管，本方案不碰。

**⚠ 分水岭铁律（按部署形态判定，不由"是否个人"判定）**：
蒸馏原文是否入库，取决于**数据物理落在哪**——即部署形态，**与"用户是个人还是机构"正交**：
- **公有云 SaaS（数据在知微云端）= 一律 `distilled_only`，永无原文**。无论租户是 2B 教育局/集团（非个人公有租户、license 在线门禁），还是 2C 个体教师（个人会员），只要数据在知微云端，**都不得存授权版本原文**（2026-07-18 拍板）。
  → 因此"非个人的公有租户（某教育局/集团）"**同样受分水岭约束、无原文**，只是它在 cloud 侧是 license 续期制的 2B 集团、走在线门禁，与 2C 个人的计费/会员体系不同，但在"无原文"这一点上完全一致。
- **私有化（数据不出校）= `private_original`**，授权版本原文可随下发包进客户机房（唯一例外）。
- cloud 运营平面里 school 产品线下作为 `1-0` 源，自身只存 `distilled_only`（结果+embedding，无原文）；原文库只留本地开发机，不下发到任何 SaaS 实例。

**常见误判**：把"非个人公有租户"当成"机构所以能放宽原文"——错。机构/集团在 SaaS 形态下仍是云端多租户，受同一分水岭约束。

### 1.5 `1-0` school 公共数据完整清单与体积/频率分级（MVP 分片依据）

| `1-0` 子集 | cloud 源表（规划，school 产品线下） | 现有对应 school 表 | 体量级 | 变更频率 | 下发策略 |
|---|---|---|---|---|---|
| 教材版本目录 | `cloud_school_tb_textbook_version` | `tb_textbook_version` | 小（~649KB） | 低（每学期微调） | 整包下发 |
| 课标条款 | `cloud_school_tb_standard_clause` | `tb_standard_clause` | 中（~1587 行） | 低（课标改版才变） | 整包 / 按学段分片 |
| 教材-课标映射 | `cloud_school_tb_version_standard_map` | `tb_version_standard_map` | 中（~763 行） | 随上两者 | 随教材版本整包 |
| 知识图谱节点 | `cloud_school_tb_kg_node` | `tb_kg_node` | 中（~7132 行） | 中（随教材/知识点演进） | 按学科分片 |
| 知识图谱边 | `cloud_school_tb_kg_edge` | `tb_kg_edge` | 中（~8606 行） | 中 | 按学科分片 |
| 蒸馏素材底料 | `cloud_school_tb_lesson_source` | `tb_lesson_source`（32 分区 + `vector(1024)` + HNSW） | **大（~795MB）** | 高（模型/底料升级频繁） | **按 (学科,年级) 增量分片，禁止整包** |
| 讲义蒸馏产物 | `cloud_school_tb_lesson_lecture` | `tb_lesson_lecture` | 小（~299 行） | 中 | 随素材底料分片 |

| 平台标准模板 | `cloud_school_template`（新建） | （无，学校自建模板属本地覆盖） | 小 | 低 | 整包 |

## 2. 总体架构：cloud 里 school 产品线下 `1-0` 源 + school 两类消费方

```
                    ┌─────────────────────────────────────────────┐
                    │   cloud 运营平面 · school 产品线（1 轴）         │
                    │   └─ 1-0 school 公共数据 · 单一事实源           │
                    │  - 课标/教材版本/知识图谱/蒸馏素材/标准模板/全国学校目录 版本库 │
                    │  - 模板库（标准模板）                          │
                    │  - 版本号 + 审计 + 灰度/全量下发                │
                    │  - 自身仅存 distilled_only（无原文）            │
                    └───────────────┬─────────────────────────────┘
                                    │  版本化下发（licensed 范围，仅限 school 产品线）
              ┌─────────────────────┴──────────────────────┐
              ▼                               ▼              ▼
   ┌────────────────────┐      ┌────────────────────┐   ┌──────────────────┐
   │ 公有云 SaaS · 2B集团 │      │ 公有云 SaaS · 2C个人 │   │ 私有化租户实例      │
   │ (教育局/集团租户)     │      │ (个体教师会员)        │   │ (客户机房不出校)    │
   │ license 在线门禁续期  │      │ 会员计费,无 license  │   │ license 离线验签    │
   │ storage=distilled_   │      │ storage=distilled_   │   │ storage=           │
   │   only **无原文**     │      │   only **无原文**     │   │   private_original │
   └──────────┬─────────┘      └─────────┬──────────┘   │   (可含原文)        │
              └──────────────┬───────────┘              └────────┬────────────┘
                             ▼                                  ▼
            公有云 SaaS 实例（数据在知微云端，双子分支同源同约束）  私有化实例本地库
                             └──────────────┬───────────────────┘
                                            ▼
            school 合并层（复用现有 ListTextbookVersions 逻辑）：
            1-0 源快照 × 本地覆盖  →  教师端最终可见/可用配置
```

**关键设计点**：
- 公有云 SaaS 的两个子分支（2B 集团 / 2C 个人）**共享同一套"云端多租户 + distilled_only 无原文"约束**，仅计费/license 形态不同（见 §0.5 授权分层）；在 `1-0` school 公共数据处理上完全一致。
- school 端的"合并层"（1-0 源 × 本地覆盖）**代码可复用**——只是"1-0 源"从「本地 `tb_*` 表」改为「cloud 下发来的快照表（如 `tb_textbook_version_snapshot`）」。本地覆盖逻辑（`school_textbook_override`、优先级班级>年级>学校）完全不动。
- **边界声明**：本架构只涉及 school 产品线（`1-0` → school 自身实例）。mfg 的 `2-0`、审计的 `3-0` 在 cloud 各自产品线下托管，走各自的下发链路，本方案不画、不碰。

## 3. 公有云 SaaS 租户（2B 集团 + 2C 个人，同源同约束）：云端直读 / 近实时同步

> 覆盖两类租户：**2B 教育局/集团租户**（license 在线门禁续期）与 **2C 个体教师**（会员计费、无 license）。两者在 `1-0` school 公共数据处理上**完全一致**：数据都在知微云端、都 `distilled_only`、**都无原文**（分水岭铁律 §1）。

- **模式**：school 实例持有 cloud 下发的 `1-0` 快照表（带 `source_version` 字段标记版本）。
- **同步触发**：
  - 启动/部署时拉取一次（确保新实例即源同源）；
  - 定时（如每 6h）或 cloud webhook 推送增量（课标改版时准实时生效）；
  - 拉取即写快照表，写前校验（行数下限、外键完整——即 2026-08-08 `verify_distill_base` 思路下沉到"下发环节"）。
- **storage_mode**：`distilled_only`，与现状一致。
- **假绿防护**：快照写入后跑"底座非空 + 引用完整"断言；CI/在线回归对快照表生效（取代原先对本地手灌表的断言）。

## 4. 私有化租户：license 鉴权 + 拉快照（重点答用户之问）

私有化实例**数据不出校、cloud 物理够不着客户机房**，故"cloud 集中维护"在私有化场景**不能直接等于"云端直读"**，必须走**下发/快照**：

1. **源在 cloud（school 产品线下）**：`1-0` school 公共数据的权威版本由 cloud 运营平面里 school 产品线下维护（与 SaaS 同源同版本）。
2. **授权范围拉取**：私有化实例用其 license key（cloud 签名+有效期）向 cloud 拉取**授权范围内的 `1-0` 快照**。未授权版本/学科不返回。
3. **本地落库**：拉来的快照写入私有化实例本地库（表结构与 SaaS 快照一致），**合并层逻辑完全复用**。
4. **storage_mode 差异（唯一实质差异）**：私有化 `storage_mode='private_original'`——因私有化不受 SaaS 分水岭限制，授权版本的**原文可随下发包进客户服务器**（2026-07-18 拍板）。SaaS 则仅 `distilled_only`。
5. **离线可用**：快照存本地，断网照常运行；下次心跳/续期再增量同步新版本（对齐 2026-07-29 私有化 license 离线验签模型）。
6. **版本治理**：client 记录 `source_version`；cloud 升级 v2 时私有化可暂不升级（客户选择），但需"兼容性声明"——school 端 RAG/教材解析按自身快照版本工作，**不假设永远最新**。

**私有化相对现状的唯一变化**：`1-0` school 公共数据的"源"从「私有化包手工 rsync」改为「cloud 授权拉取快照」。根治逻辑（建表+校验+同源）必须内建在下发环节，否则只是把假绿从包里挪到别处。

## 5. cloud 运营端 MVP 设计（P2 量级，非顺手改）

cloud 当前已有 0 轴平台能力（heartbeat / Token供方 / 统一身份，见 §9.4），**但 school 产品线的 `1-0` 公共数据尚未在 cloud 里建源表、维护 UI、下发机制**，需新建——挂载在 **cloud 运营平面 · school 产品线（1 轴）下**，不是 0 层平台能力。

### 5.1 `1-0` 源数据模型（cloud 侧，school 产品线下）

统一加 `source_version`（语义化版本，如 `2026.08.1`）+ `data_kind`（区分 `1-0` 子集）+ `checksum`（内容哈希，供实例校验一致性）。

| 源表（cloud · school 产品线） | 对应现有 school 表 | 关键字段（对齐现有） | 体积/下发策略 |
|---|---|---|---|
| `cloud_school_tb_textbook_version` | `tb_textbook_version` | `version_key, xue_duan, nian_ji, xue_ke, jiao_cai_ming, chu_ban_she, ban_ben_biao_shi, ce_bie, mu_lu_url, inferred` + `source_version` + `data_kind='textbook'` | 649KB，整包下发 |
| `cloud_school_tb_standard_clause` | `tb_standard_clause` | 现有字段 + `source_version` + `data_kind='standard'` | 中，整包/按学段分片 |
| `cloud_school_tb_kg_node` / `cloud_school_tb_kg_edge` | `tb_kg_node` / `tb_kg_edge` | 现有字段 + `source_version` | 中，按学科分片 |
| `cloud_school_tb_lesson_source` / `cloud_school_tb_lesson_lecture` | `tb_lesson_source` / `tb_lesson_lecture` | 现有字段（`tb_lesson_source` 含 `vector(1024)` + HNSW，**仅 distilled，无原文列**） + `source_version` | **795MB，按 (学科,年级) 增量分片下发，禁止整包** |
| `cloud_school_tb_school_directory` | 全国 K12 学校目录（纳入 `1-0`） | 省/市/区/学校/学段 等 | 中，整包 |
| `cloud_school_template` | 标准模板（新建） | `id, kind, payload, source_version` | 小，整包 |

> 分水岭约束：`cloud_school_tb_lesson_source` **只有 distilled 结果列，无原文列**（与 §1 铁律一致）。私有化下发包由"源 + 本地授权原文补丁"合成，原文不进 cloud。

### 5.2 下发 API 契约（cloud 侧，school 产品线下）

```
GET /api/cloud/school/public-data/pull
  Headers: Authorization: Bearer <license_or_session>   # SaaS 用平台 session；私有化用 license key
  Query:
    data_kind   = textbook|standard|kg|lesson_source|school_directory|template   (必填)
    version     = <source_version> 或 "latest"                  (默认 latest)
    slice       = <分片键>  例: lesson_source 用 "math/G7"        (大表必填, 防整包)
    since       = <checksum 或 version>                          (增量: 仅返回变化)
  Response 200:
    {
      "data_kind": "lesson_source",
      "version": "2026.08.1",
      "slice": "math/G7",
      "checksum": "<sha256 of payload>",
      "records": [ ... ],          # 增量时仅含变更行; 全量时全部
      "deleted_ids": [ ... ]       # 增量时本版本移除的行
    }
  Response 403: license 无效/过期/超出授权范围(data_kind 或 slice 不在授权内)
```

- **鉴权分层**（复用 cloud 现有 IdP + License 机制，边际成本低）：
  - SaaS 2B 集团走 license 在线门禁（续期制）；
  - SaaS 2C 个人走会员 session；
  - 私有化走 license 离线验签（cloud 公钥，参见统一身份方案 §5.5）。
- **授权范围**：license 绑定 `data_kind` + `slice` 白名单（例：某集团只购了"数学/语文"两科，则 `lesson_source?slice=english` 返回 403）。
- **R7 防护**：响应头固定 `X-Storage-Mode: distilled_only` 给所有 SaaS 调用；私有化才返回 `private_original`。实例侧断言不一致即拒绝写入并告警。

### 5.3 源数据生命周期（MVP 内部流程）

```
数据团队产出 JSON/蒸馏包
   │  (本地蒸馏，原文库只留开发机，见分水岭)
   ▼
运营 UI（school 产品线下）录入/导入 → 写入 cloud 源表（带 draft 标记）
   │
   ▼
发布：生成新 source_version + 计算 checksum + 写 cloud_school_public_data_release(version, tenant_allowlist, status)
   │
   ▼
灰度：仅 allowlist 指定 tenant 拉到新版本（pull 时 latest 回落判定）
   │
   ├─▶ 实例侧 pull → 写本地 _snapshot → 校验(行数/外键/version/mode) → 合并层生效
   │
   ▼
审计：记录每次 pull(tenant, data_kind, slice, version, at)
回滚：allowlist 指回旧 version（发布即不可变，无销毁）
```

### 5.4 运营 UI（P1，数据团队用，非师生端）

最小集：school 产品线 `1-0` 源列表/查看、版本对比（diff 两 `source_version`）、录入/编辑（JSON 导入或表单）、发布（生成新 `source_version` + checksum）、灰度标记（指定 tenant 白名单先吃新版本）、回滚（指向旧 `source_version`）、审计日志（谁/何时/改了哪版/下发给谁）。

> 运营 UI 是 cloud 运营平面里 **school 产品线**的"数据团队工作台"，与 0 轴平台能力（heartbeat / Token供方 / 统一身份）分属不同轴，互不混淆。进入 school 产品线的运营人员 / Agent / 知了助手，只在此边界内操作 `1-*`。

### 5.5 灰度 / 回滚 / 审计

- **灰度**：`cloud_school_public_data_release` 表含 `(data_kind, version, tenant_allowlist, status)`；`pull` 时若 `latest` 且 tenant 不在新版本 allowlist，则回落上一稳定版。
- **回滚**：发布即不可变（新 version），回滚=把 allowlist 指回旧 version，无销毁。
- **审计**：每次 `pull` 记 `(tenant, data_kind, slice, version, at)`，供追溯。

### 5.6 工作量拆分（建议立项顺序）

| 阶段 | 内容 | 产出 |
|---|---|---|
| M0 | cloud 里 school 产品线下 `1-0` 源表 + 抽取现有 seed 为 v1 | cloud 有源、版本号 |
| M1 | `pull` API + 鉴权 + 分片/增量 | SaaS/私有化可拉 |
| M2 | school 端快照拉取 + 双读过渡（§6） | 漂移根治 |
| M3 | 运营 UI + 灰度/回滚/审计 | 数据团队可自助维护 |
| M4 | 私有化 license 拉快照改造 | 私有化同源 |

## 6. 迁移路径（school 端：双读过渡，零停机切换）

目标：把 `ListTextbookVersions` 等读取从「本地 `tb_textbook_version` 等」切到「cloud 下发快照表」，期间可回退，绝不破坏现有本地覆盖合并层。

### 6.1 表改造（school 端）

- 现有本地 `1-0` 公共数据表重命名为**遗留表**：`tb_textbook_version` → `tb_textbook_version_legacy`（数据保留，不删）。
- 新增**快照表**：`tb_textbook_version_snapshot`（结构同 legacy + `source_version` + `checksum`），由下发写入、只读。**本地覆盖表 `school_textbook_override` 不动。**
- 其他 `1-0` 公共数据表（`tb_standard_clause` / `tb_kg_*` / `tb_lesson_source*` / `tb_lesson_lecture*` / 全国学校目录表）同此模式：legacy 保留 + `_snapshot` 新表。

### 6.2 双读开关（核心安全网）

`cmd/server/main.go` 新增配置项 `A_SOURCE_MODE`（环境变量，默认 `legacy` 先不切）：

```
A_SOURCE_MODE = legacy      → 读 *_legacy（行为同今日，零风险）
A_SOURCE_MODE = snapshot    → 读 *_snapshot（cloud 下发）
A_SOURCE_MODE = dual        → 双读比对：以 legacy 为主返回，异步比对 snapshot 差异并打 WARN 日志（观测期）
```

- **迁移节奏**：
  1. 部署 M2，设 `A_SOURCE_MODE=legacy`（线上无感）。
  2. 启动快照拉取任务（首次全量对齐 v1），写 `_snapshot` 表。
  3. 切 `dual` 跑 1~3 天，观测 WARN（legacy vs snapshot 差异）→ 差异必为 0 才进下一步。
  4. 切 `snapshot` 正式生效。
  5. 稳定后 `legacy` 表可归档（保留 1 个版本周期再删）。
- **回滚**：任何异常 → 改 `A_SOURCE_MODE=legacy` + 重启，秒级回退，不用动表。

### 6.3 读取层改造（复用现有逻辑）

`ListTextbookVersions`（it_repo.go:86）仅改数据源：
- `legacy` 模式：`FROM tb_textbook_version`（现状）。
- `snapshot` 模式：`FROM tb_textbook_version_snapshot`。
- **合并层不变**：无论哪种模式，都 `LEFT JOIN school_textbook_override` 做"产品线源 × 学校覆盖"合并（本地覆盖逻辑 0 改动）。

### 6.4 快照拉取守护（school 端 daemon / 定时）

- 启动时拉一次（确保新实例即源同源）；之后每 N 分钟（默认 30）或 cloud webhook 触发增量 `pull`（带 `since=本地 checksum`）。
- 写入前**内建校验**（根治假绿下沉，对应 R2）：
  - `tb_lesson_source_snapshot` 行数 ≥ 下限阈值（如 50000）；
  - `tb_lesson_lecture_snapshot` 行数 ≥ 下限；
  - `lecture_id` 外键悬空 = 0；
  - `source_version` 与 cloud 返回一致；
  - storage_mode 断言：SaaS 实例必须为 `distilled_only`（R7）。
  - 任一失败 → 拒绝覆盖旧快照、保留上次可用、发告警（不静默）。
- 写入用事务 + 先写临时表再原子 rename，避免半截数据被读。

### 6.5 私有化改造

- 私有化实例部署/续期时，把"手工 rsync 私有化包"改为"用 license 向 cloud `pull` 授权范围快照"写本地 `_snapshot` 表。
- `storage_mode=private_original`：拉取后，由本地"授权原文补丁"（随私有化交付、不进 cloud）补回原文列。
- 其余合并层、双读开关与 SaaS 完全一致。

### 6.6 下线手工 seed + 断言升级

- `cmd/seed/knowledge`、`cmd/seed/textbook_versions` 等手工 TRUNCATE 重灌**退役**（改由 cloud 下发驱动），消除环境漂移根因（这是 2026-08-08 假绿的根）。
- `verify_distill_base.cjs` 升级：从"查本地 `tb_*`"改为"查 `_snapshot` 表 + 校验 `source_version` 与 cloud 一致 + storage_mode 断言"，CVM cron 在线跑；并新增 cloud 侧断言（源库行数/checksum 与下发一致）。

## 8. 结论与建议

用户直觉**方向正确且对 school 产品线公共数据（`1-0`）成立**：cloud 作为 school 产品线下 `1-0` 单一事实源 + 版本化下发，能根治"多环境手工灌导致漂移/假绿"，且天然覆盖 school 的两类消费方——公有云 SaaS（2B 教育局/集团 + 2C 个体教师，**同源同约束、均无原文**）、私有化（拉授权快照、唯一可含原文例外）。分水岭按**部署形态**判定而非"是否个人"，非个人公有租户同样受 `distilled_only` 约束（见 §1 铁律与 R7）。

重点澄清：**课标/教材版本/知识图谱/蒸馏素材/标准模板/全国 K12 学校目录，是 `1-0`（school 产品线公共数据），不是平台 0 层数据**；它们由 cloud 运营平面托管维护，但归属 school、不跨产品线。0 轴平台能力（heartbeat `0-1` / Token供方 `0-2` / 统一身份 `0-3`）与之性质不同、互不重叠。这正对应"按产品线进入"的边界设计：运营人员 / Agent / 知了助手进入 school 只看 `1-*`，不会误碰平台能力或其它产品线的数据。

建议：**先立项、出 cloud 里 school 产品线下 `1-0` 运营端 MVP（源存储 + 下发 API + SaaS 快照拉取），私有化改造随其后**，手工 seed 在整个链路打通后退役。

下一步：用户拍板是否立项；若立，先细化 §5 运营端 MVP 与 §6 迁移双读过渡方案。

## 9. 层级模型正解（用户 2026-08-09 最终校准）

> 本节把"平台公共（0 轴）vs 产品线（1/2/3 轴）"两套正交编号轴讲清，作为全文唯一权威层级定义。

### 9.1 两级编号轴

| 轴 | 含义 | 节点示例 |
|---|---|---|
| **0 轴 · 平台级公共（跨产品线，cloud 底座）** | 不属于任何产品线、被所有产品线共用的平台能力 | `0-1` heartbeat ｜ `0-2` Token 供方管理（采购算力·百炼）｜ `0-3` 统一身份（IdP/租户/License） |
| **1 轴 · school 产品线** | school 自己的产品线，进入后才有它内部的公共数据与运营节点 | `1-0` school 公共数据（课标/教材/图谱/蒸馏/模板/全国 K12 学校目录）｜ `1-1` 租户·License ｜ `1-2` Token 计量 ｜ `1-3` 流量计量 ｜ `1-4` 工单 ｜ `1-5` 个人用户 |
| **2 轴 · mfg 产品线** | 知微智造（WMS） | `2-0` mfg 公共数据（如有）｜ `2-1` 租户·License ｜ `2-2` 模块管理 ｜ … |
| **3 轴 · 审计产品线** | 知微 AI 审计 | `3-0` 审计公共数据（预留）｜ … |

**读图要点**：
- `0-*` 的 `* `是"平台能力序号"；`1-0` 的 `0` 是"school 产品线下的公共数据节点"（产品线内还可能有 1-1 租户、1-2 计量…）。两套编号不可混为一谈。
- `1-0 / 2-0 / 3-0` 各自归属对应产品线，**不跨产品线共享**；但都统一由 **cloud 运营平面托管维护**（"放在 cloud 里各产品线的名下"）。
- **按产品线进入**：运营人员 / Agent / 知了助手，进入 school 产品线只看 `1-*`，进入 mfg 只看 `2-*`，边界分明，不会把 school 的课标数据误当成平台公共数据，也不会跨产品线串数据。

### 9.2 架构简图（平台 0 轴 + 三条产品线轴）

```
═══════════════════════════ cloud 运营平面（统一托管/维护）═══════════════════════════
知了（运营/运维 AI 助手）贯穿各节点，标注 [知了] 处由其协助

0. 平台级公共（0 轴 · 跨产品线，cloud 底座，不属于任何产品线）
   0-1  heartbeat（心跳/存活监测，[知了]协助）
   0-2  Token 供方管理（采购算力·百炼，配额/账单/路由）
   0-3  统一身份（IdP / 租户 / License，[知了]辅助归集）
```

## 10. 验收标准 / Definition of Done（供立项评审）

本方案视为"完成"的判定门槛（不碰代码，仅列标准）：

| 维度 | DoD 条目 |
|---|---|
| **同源** | staging / prod / 任意 school 私有化实例 的 `1-0` school 公共数据 `source_version` 均可追溯至同一 cloud 源（cloud 里 school 产品线下），无手工 seed 残留 |
| **可下发** | `GET /api/cloud/school/public-data/pull` 在 SaaS（2B/2C）与私有化（license）三种鉴权下，按 `data_kind`/`slice`/`since` 正确返回，越权返回 403 |
| **无原文泄漏** | 所有 SaaS 实例 `X-Storage-Mode=distilled_only` 且本地库无原文列；私有化 `private_original` 仅含授权版本原文、不进 cloud |
| **可回退** | `A_SOURCE_MODE` 三态可用，dual 观测期差异=0 方切 snapshot；异常改 legacy 秒级回退 |
| **假绿根治** | CVM cron `verify_distill_base` 断言 `_snapshot` 行数/外键/version/mode，失败即告警、不静默 |
| **可运维** | 运营 UI（school 产品线下）支持录入/发布/灰度/回滚/审计；数据团队可自助，无需 Agent 手工灌 |
| **可追溯** | 每次 pull / 每次发布 均留审计记录（谁/何时/哪版/下发给谁） |
